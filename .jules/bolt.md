
## 2026-07-07 - [JS Map as LRU Cache]
**Learning:** For interactive UI components that perform heavy repetitive math (like the 61-day timeline scrubber triggering `calculateTransits` inside `src/lib/astrology.ts`), relying solely on React `useEffect` debouncing is insufficient because multiple scrubber ticks re-evaluate the same sequence of dates rapidly. A vanilla `Map` handles LRU cleanly and quickly by combining `delete` and `set` on access to push the most recently used items to the end of its iteration order, turning O(ms) calculations into ~0ms.
**Action:** When implementing heavy computational logic bound to dynamic scrubber inputs, apply an internal LRU cache via `Map` directly on the utility side rather than just throttling the UI/React side.
## 2024-06-25 - [Constant Re-allocation Bottleneck]
**Learning:** Re-allocating static configuration objects and arrays on every function call within hot loops (e.g., `calculateAshtakavarga`, `checkVedha`) can dramatically slow down heavy iterative logic like a 61-day timeline calculation, causing significant GC pressure and wasted CPU cycles. Even for small objects, hoisting them to module scope can result in >10x micro-benchmark improvements in execution time for those specific operations.
**Action:** Always inspect frequently called utility functions for internal constant object/array declarations. Move immutable configuration mappings, rules sets, and static lookups to the module/global scope.
## 2026-07-08 - [Ashtakavarga Calculation Bottleneck]
**Learning:** In highly iterative contexts like the interactive 61-day scrubber timeline, `calculateAshtakavarga` was doing heavy object allocation (`new Array(12).fill(0)`) and performing multi-level nested loops inside dynamically scoped lookups. By extracting the fixed astrological rules into flat precomputed bitmasks (`Int32Array`) at module scope, allocating objects once per run, and replacing nested loop searches with bitwise checks (`rule & (1 << offset)`), `calculateAshtakavarga` runtime improved by ~20x. Additionally, modifying `checkVedha` to use a standard `for` loop instead of `Array.prototype.find` yielded another measurable speedup by avoiding creating an arrow function closure each time.
**Action:** When working with nested array rules and mapping operations in hot paths, flatten the nested loops into bitmask lookups, avoid inner loop closures like `.find()` or `.forEach()`, and aggressively pre-allocate objects and maps outside function scope or loops where applicable.
## 2026-07-10 - [Zero-Allocation Loops for Timeline Calculations]
**Learning:** Re-allocating arrays implicitly using literals (e.g., \`["Jupiter", "Venus", "Mercury", "Moon"].includes(...)\`) and creating arrow functions (via \`.forEach()\`, \`.find()\`) inside hot paths like \`calculateGocharaScore\` generates severe garbage collection overhead. In an interactive interface that renders a 61-day timeline, these micro-allocations get multiplied by the number of days evaluated, causing measurable CPU hitching on lower-end devices. Using module-scoped pre-computed bitmasks (e.g., \`BENEFIC_HOUSES_MASK\`) and standard \`for\` loops dropped execution time for \`calculateGocharaScore\` by over 50%.
**Action:** In nested calculative processes meant for timelines or heavy scrubbers, eliminate implicit arrays, avoid \`.includes\` on small static datasets by using flat logical ORs, switch \`.forEach\`/\`.find\` to standard \`for\` loops, and use bitmasks for subset containment checks.
## 2024-05-18 - [Replacing O(N^2) Array .find with Parallel Index Assignment]
**Learning:** In the `calculateTransits` Vedha loop, assigning computed results back to the original `planets` array using `planets.find(tp => tp.name === p.name)` created a severe O(N^2) bottleneck. This codebase uses `.map` heavily to generate relational arrays (like `planetsFromMoon`), which perfectly preserves the 1:1 index alignment with the source array.
**Action:** When a mapped or identically ordered array needs to feed data back into its source array, avoid using `.find()`. Instead, use a standard `for (let i = 0; i < arr.length; i++)` loop and assign the result directly via `sourceArray[i].prop = mappedArray[i].prop`.
## 2026-07-28 - [Timeline Scrubber UX Intent vs Caching]
**Learning:** In interactive timeline components that allow a user to scrub back and forth in time, fixing the "base" calculation date and mapping the scrubber value strictly as a UI offset might seem like an intuitive optimization to avoid recalculations. However, if the intended UX design dictates that the entire timeline window *shifts* alongside the scrubber (e.g., viewing transits centered around the offset date), caching based purely on the original un-scrubbed date introduces a functional regression where the timeline freezes.
**Action:** Before optimizing loop operations that depend on an offset variable (like `scrubDays`), always trace the semantic intent of the UX: Does the offset represent a selection *within* a static window, or does it shift the center of the window itself? If the window shifts, caching must either account for the new window bounds or be abandoned in favor of optimizing the underlying math (e.g., via `for` loop refactoring instead of array methods).
## 2026-07-28 - [Overhead of Array Iterators in Hot Paths]
**Learning:** Re-allocating arrays implicitly using literals (e.g., `["Jupiter", "Venus", "Mercury", "Moon"].includes(...)`) and creating arrow functions (via `.forEach()`, `.find()`) inside hot paths generates severe garbage collection overhead. In an interactive interface that renders a 61-day timeline, these micro-allocations get multiplied by the number of days evaluated, causing measurable CPU hitching on lower-end devices. Using module-scoped pre-computed bitmasks (e.g., `BENEFIC_HOUSES_MASK`) and standard `for` loops drops execution time significantly.
**Action:** In nested calculative processes meant for timelines or heavy scrubbers, eliminate implicit arrays, avoid `.includes` on small static datasets by using flat logical ORs, switch `.forEach`/`.find` to standard `for` loops, and use bitmasks for subset containment checks.
## 2026-07-28 - [Micro-optimizations vs Readability]
**Learning:** While optimizing loops and replacing array methods like `.filter` combined with `.findIndex` (which resolves O(N^2) bottlenecks) yields massive performance benefits, blindly replacing native `.find()` calls with manual `for` loops on extremely small arrays (like the 12 planets) provides practically zero measurable speedup while significantly hurting code readability and brevity. This violates the core principle of not sacrificing readability for micro-optimizations.
**Action:** Focus array iterator replacements (like switching from `.forEach` to `for` loops) strictly on massive nested loop structures or contexts that iterate thousands of times per interaction. For simple variable extraction from small, fixed-length arrays (e.g., extracting planetary data), retain the native `.find()` methods.
## 2024-06-25 - Lazy Evaluation of Expensive Upgrahas (Shadow Planets) Calculation
**Learning:** In the `calculateTransits` pipeline, calculating 11 Upgrahas (Aprakasha and Kālavelā grahas) took a substantial proportion of overall time (around 30-40%). Since these Upgrahas are primarily used only when explicitly toggled on in the "Charts / Deep" tab, calculating them eagerly while generating the 60-day interactive timeline causes massive redundant overhead.
**Action:** Use `Object.defineProperties` inside return object constructors for expensive, optional calculations to defer them via getters (Lazy Evaluation). The getter executes the complex calculation only upon first access and internally caches the results (`_upgrahas`, `_d1WithUpgrahas`, etc.), providing immediate improvements to unrelated hot paths like timeline generation without changing component APIs.
## 2025-02-28 - Avoid O(N) array lookups during renders
**Learning:** In a highly reactive timeline scrubber like the one in `src/app/page.tsx`, performing array lookups `planets.find(...)` and filtering `timelineEvents.filter(...)` inside the render cycle becomes a performance bottleneck.
**Action:** Use `useMemo` to convert arrays to Maps for `O(1)` lookups (`activePlacementsMap`) and cache pre-filtered values (`activeSignEvents`) and concatenated strings (`timelinePathStr`) to reduce JS garbage collection and render delay.
